# Repo Driver Validation

Targeted reads only. Whole `driver.py` files were intentionally avoided.

## Validated available devices

### `community_drivers/li_ha`

- `info.txt` confirms a Tecan Freedom EVO liquid-handling workstation with aspirate/dispense, liquid-level detection, disposable tips, and plate handling.
- `registry.yaml` exposes concrete JSON-command actions for `auto-aspirate`, `auto-dispense`, `auto-pick_up_tips`, `auto-drop_tips`, `auto-pick_up_resource`, `auto-move_picked_up_resource`, and `auto-drop_resource`.
- Validation result: strong available match for pipetting plus basic plate transport.

### `community_drivers/star_backend`

- `info.txt` describes a Hamilton STAR platform with aspiration, dispensing, tip handling, liquid-level detection, plate/carrier transport, iSWAP/CoRe 96 support, and some connected heating/cooling modules.
- `registry.yaml` exposes a large action surface around liquid handling and plate movement, including CoRe gripper operations.
- Validation result: strong available match for high-throughput pipetting plus deck logistics.

### `community_drivers/vantage_backend`

- `info.txt` describes Hamilton Vantage with automated pipetting, tip pickup/ejection, `96`-head plate processing, liquid-level detection, and an integrated gripper.
- `registry.yaml` exposes aspiration, `96`-head, and CoRe96 actions.
- Validation result: strongest locally validated lead for bundle 1 and general automation support.

### `community_drivers/incubator`

- `info.txt` confirms plate storage, loading tray operations, set/get temperature, and shaking support.
- `registry.yaml` exposes `fetch_plate_to_loading_tray`, `take_in_plate`, `set_temperature`, `open_door`, `close_door`, and shaking actions.
- Validation result: good generic available incubator.

### `community_drivers/cytomat_backend`

- `info.txt` is especially strong: it explicitly says the system controls temperature, `CO2`, humidity, and `O2`, and supports shaking plus barcode reading.
- `registry.yaml` exposes storage/exposed/transfer position moves, loading-tray fetch, shaker initialization, temperature setpoint control, and door control.
- Validation result: best available incubator/hotel for cell-centric plate workflows.

### `community_drivers/incubator_shaker_stack`

- `info.txt` is coherent and confirms a stackable plate incubator/shaker with loading trays.
- `registry.yaml` exposes `open_all`, `close_all`, `start_all_temperature_control`, `get_all_temperatures`, and `shake`.
- Important caveat: the tail of `registry.yaml` appears to contain inconsistent autogenerated metadata that incorrectly labels the device as a transmission electron microscope. The action mapping itself still matches an incubator/shaker.
- Validation result: available, but metadata quality is weaker than `cytomat_backend`.

### `community_drivers/bio_shake`

- `info.txt` confirms a microplate heater-shaker with temperature control, shaking, plate lock, and possible active cooling.
- `registry.yaml` exposes `auto-set_temperature`, `auto-shake`, `auto-stop_shaking`, `auto-lock_plate`, `auto-unlock_plate`, and temperature readback.
- Validation result: good available thermoshaker for smaller plate-format substeps.

### `community_drivers/centrifuge`

- `info.txt` confirms door control, indexed bucket positions, sample load/unload, and timed spin cycles at specified `g`.
- `registry.yaml` exposes `open_door`, `close_door`, `lock_door`, `unlock_door`, `go_to_bucket1`, `go_to_bucket2`, `start_spin_cycle`, `spin`, `load`, and `unload`.
- Validation result: strong generic centrifuge match and better suited than the plate-only VSpin candidates for the phage workflow rewrite.

### `community_drivers/sealer`

- `info.txt` confirms thermal microplate sealing with temperature control.
- `registry.yaml` exposes `seal`, `open`, `close`, `set_temperature`, and `get_temperature`.
- Validation result: available and adequate for plate sealing.

### `community_drivers/peeler`

- `info.txt` confirms automatic microplate film removal before pipetting or readout.
- `registry.yaml` exposes `peel` and `restart`.
- Validation result: available and adequate for de-sealing.

### `community_drivers/plate_reader`

- `info.txt` confirms absorbance, fluorescence, and luminescence readout.
- `registry.yaml` exposes `assign_child_resource`, `open`, `close`, `read_absorbance`, `read_fluorescence`, `read_luminescence`, and `get_plate`.
- Validation result: available generic reader.

### `community_drivers/molecular_devices_backend`

- `info.txt` confirms multimode absorbance, fluorescence, luminescence, fluorescence polarization, and time-resolved fluorescence, plus onboard temperature control and shaking.
- Validation result: best validated ELISA/clone-screening reader because it covers both readout and some plate-conditioning features.

### `community_drivers/bio_tek_plate_reader_backend`

- `info.txt` confirms absorbance, fluorescence, luminescence, temperature control, shaking, wavelength-range queries, and version/status functions.
- Validation result: strong alternative reader.

## Missing or weakly validated items

### `existing_device_infos/`

- The plan expected `community_drivers/existing_device_infos/`, but no such directory exists anywhere under `Uni-Lab-OS/`.
- Result: no extra repo-based enrichment was possible from that source.

### Standalone robot-arm / AGV candidates

- CSV results mention `robotic_arm.UR`, `robotic_arm.elite`, `agv.SEER`, and similar entries.
- No corresponding `community_drivers/<device>/` directories were found in the local tree during targeted validation.
- Result: these remain CSV-only matches and were not used as primary recommendations where a locally validated integrated gripper workstation already existed.

### Flow cytometer / FACS / colony picker / sequencer / AKTA / Biacore

- Targeted repo searches did not reveal locally available directories for these device classes.
- Result: they remain genuine gap areas and move to explicit web-backed recommendation status.

## Registry scanner sanity note for `driver_guessed.py`

- `unilabos/registry/ast_registry_scanner.py` collects every `.py` file under the scan root as long as the filename does not start with `__`.
- The relevant code path is the `_collect_py_files()` helper, which appends any matching `.py` file before AST parsing.
- Result: the intentionally named `driver_guessed.py` files are discoverable by the AST scanner and do not need to be renamed to `driver.py` for basic registry discovery.
